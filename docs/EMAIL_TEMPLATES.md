# Xoot Email Template Playbook

Brevo email is for records, receipts, longer summaries, and lifecycle nudges. In-app notifications remain the primary operational channel.

## Safety Rules

- Never email OTPs, passwords, card details, gate codes, alarm codes, lockbox codes, full access instructions, identity documents, private household notes, or support complaint details.
- Email should point users back to the authenticated Xoot app for live booking, payment, address, support, and sensitive access details.
- Payment success is never trusted from email or frontend state. Payment state must come from verified provider callbacks or audited admin action.
- Marketing claims must not include fake testimonials, fake partnerships, fake scarcity, unsupported availability, or competitor attacks.

## Brevo Setup Needed

1. Create transactional templates using the template keys above.
2. Verify sender domain with SPF, DKIM, and DMARC.
3. Store `BREVO_API_KEY`, sender email, sender domain, template IDs, and webhook key as Edge/backend secrets only.
4. Add webhook validation before consuming bounce, complaint, or engagement webhooks.
5. Smoke-test template rendering with staged accounts before production traffic.

## Invoice Email Rules

- Invoice emails may attach or link only the original private PDF path generated by `generate-booking-invoice`.
- `resend-booking-invoice` must queue `booking_invoice_resend` with the existing `pdf_path`; it must not regenerate a new invoice.
- Invoice PDFs must not include gate codes, alarm codes, private household notes, identity documents, or internal support notes.
- Invoice legal entity, VAT rate, and VAT number values belong in Supabase Edge Function secrets, not frontend or mobile env files.
