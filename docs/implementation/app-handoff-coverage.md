## 14 October 2026 — founder corrections to the design handoff (work in progress)

The founder clarified two non-negotiable product requirements that supersede misleading copy in the September handoff assets, without treating the remaining screens as complete:

- **Cadence:** all five bookable service types must initialise to `weekly` with precisely the chosen first visit's weekday selected on website and Expo. Customers can change to once or fortnightly; service changes preserve explicit cadence. Date changes move the mandatory first repeat day instead of adding an accidental extra weekly visit; manually selected extra days are preserved. The UI still needs live authenticated and physical-device verification.
- **Gift a Clean:** 52 weekly visits are needed for one year. Existing selectable 1/3/4/6/12 bundles remain individual visits, with `12` correctly described as about three months at one per week, and `6` no longer described as half a year. Do **not** offer 52 visits as a payable product while server `GIFT_COUNTS` and fulfilment only support existing bundles. Source prototype `app/Gift.jsx` contains inaccurate 12/6-year copy, overridden intentionally in production components.
- **Design acceptance remains open:** a build passing and a deployed marketing page are not proof of the full handoff. The entire table above, mobile device screenshots, source typography/dimensions/interactions, authenticated routes, crew and contractor screens, help/account screens and real provider actions must be completed and compared screen-by-screen. Do not close this ledger until every route has visual and behavioural evidence, including payment/calling unavailable states as appropriate.

This change is isolated from the active Codex PR #46 and targets the founder-approved `release/xoot-production` branch. It changes UI defaults and copy only; there is **no automatic recurring booking submission**, charged annual gift or enabled provider checkout.

## 15 October 2026 — native Visit Detail and Tracking UI slice

New owner-bound Expo route `/visits/[id]` from real Visits cards. It displays a selected booking from `useNativeCoreData()`, whose queries require the authenticated owner's user ID, and handles loading, unauthenticated, missing/invalid ID and read errors without exposing another user's booking. Source-inspired `app/Visits.jsx` / `app/Tracking.jsx` cards show real recorded service, scheduled time, address, assignment, optional verified Xooter rating/identity and current server status. Status journey labels are **indicative only**, not fabricated historical event timestamps. A rebooking link opens the actual booking input flow and support opens Concierge. Unverified live location/ETA, chat/voice, checklist tasks, rating writer and financial settlement are expressly unavailable, not simulated. The native Visits list no longer advertises `bookings.price` as a settled paid total.

The native `scripts/native-visit-detail.test.mts` suite checks read-only status narratives, the owner-bound route, safe UUIDs, no fake ETA/refund and service rebooking; CI includes this alongside native gift/booking tests. **Full source fidelity, authenticated staging, real device screenshots, crew state events, verified ledger/receipt, chat/calls, checklist and true tracking remain open**. This is a UI coverage increment, not completion of the entire website/mobile handoff.

**Account-switch privacy finding and fix:** The pre-existing native `NativeCoreDataProvider` could briefly expose the previous account's cached booking/profile data on the first render after an authentication change, before its refresh effect cleared/replaced it. The provider now tags loaded data by owner ID and returns blank bookings, profile and unread counters, with loading state, unless the current user ID matches. This guard applies to Home, Visits, Visit Detail and other consumers. Native source-level regression asserts the guard; real two-account device tests remain required.

## 15 October 2026 — native Xooter job offers and recorded earnings slice

The original `app/Xooter.jsx` contrasts Xooter work (denser, factual, income-first) with the customer interface; its sample Nomsa bookings, R2,840 paid-out figure, weekly Friday payout, invented route ETA and training grades **are not production facts**. This slice replaces the Expo `/xooter/jobs` shortcut placeholder with live, access-controlled job cards, and adds a dedicated `/xooter/earnings` ledger screen.

- `/xooter/jobs`: signed-in `xooters` identity lookup by `user_id`, then production `get-xooter-job-cards` Edge function (deployed and backed by `get_xooter_job_cards_for_user`). Strict success/data/jobs response validation rejects cross-worker records; only service, offered/accepted/history status, date and duration are projected, excluding customer ID, address and all access codes even when present in the privileged API response. Native job responses remain in the existing authenticated website workspace `/xooter/jobs`, reached by an explicit link: the `ops-workflow` accept/decline transaction must receive a correctness review before duplicating writes natively. No photo/checklist/ETA spoofing.
- `/xooter/earnings`: account-scoped `xooter_earnings` query filtered by current Xooter ID and rolling 7/30-day UTC lookback, bounded to 101 rows and displays max 100. Clearly marks truncation and only sums records shown; all money is Postgres-authored rand amounts. Pending rows distinguished, but no ledger status or net figure is presented as proof of bank settlement. No invented weekly payout or commission grade.
- `/account`: links to Xooter Jobs as a discoverable work entry. All signed-in views remount on account switches and clear prior records while fetching. Guests and users without a Xooter row receive an honest sign-in/verification path, not a mock dashboard.
- `mobile/scripts/native-xooter-ledger.test.mts`: covers Edge envelope, cross-worker rejection, sensitive field stripping, strict finite monetary records, seven/thirty-day ranges, route access and absence of fabricated payout or private addresses. CI requires these tests plus Expo typecheck, lint, full web tests and approved design/browser gate.

**Remaining**: physical iOS/Android screenshot comparisons, accepted-address access window UX, secure per-field reveal/audit, atomic job response and crew/checklist migration, real earnings settlement reconciliation, actual payout statements, commission/boost contract, Xooter KYC and training/growth screens. No client access code or payment capability was enabled in this slice.

## 15 October 2026 — Xooter job-detail and complete-period ledger continuation

The baseline Xooter Jobs/Earnings native source was already merged in PR #56. No destination address, gate/alarm code, customer identity, invented ETA, job pay, payment receipt or native job-response write is displayed. Deep-linked IDs are validated, ownership is rechecked against `get-xooter-job-cards`, and switching user or job identity remounts and invalidates prior state.

Native `/xooter/earnings` now supports **keyset-based incremental history** using server-authored `created_at` and UUID keys, an owner-filtered RLS read, a fixed per-refresh snapshot and a rolling 7/30-day selection. It loads at most 51 records per request, shows 50 new entries at a time, permits load-more until the selected period has no further entries, and never labels the partial subtotal as a complete-period total. Doubled or malformed/mixed-owner ledger records and unsafe cursor input fail closed. Amounts are checked for exact cent precision and aggregated in safe-integer cents before currency formatting. Ledger amounts remain *recorded earnings*, not bank payout evidence.

Privacy/correctness release checks: new source/negative tests cover exact cents (including fraction/overflow), safe job UUIDs, account/period remounting, live server projection only, time/snapshot-bound keyset filtering, no fabricated access or payment statements and keyset pagination controls. ## 16 October 2026 — native Xooter Home dashboard continuation

The approved 3 September Xooter design includes a worker Home screen, but the existing Expo application previously exposed Jobs, Earnings, KYC and Training only as separate account links. This isolated continuation adds `/xooter` with the original Xooter visual hierarchy (personalised greeting, lead card, today's visits, compact summary metrics and growth/work shortcuts), adapted to Xoot's actual authenticated backend.

- **Owner and eligibility:** `xooters` is read with `user_id = current auth user` and only `id,user_id,active,background_check_status`; the production catalogue confirms these fields and RLS enabled. Profile existence alone is not verification: job-card requests proceed only for `active && background_check_status === 'approved'`. A pending/unverified worker sees verification/training routes instead of fictional work.
- **Job cards:** use deployed `get-xooter-job-cards` (ACTIVE, JWT-verified), parse the owner-specific projection with the existing private-field-stripping utility, and display only accepted jobs in today's schedule. Job offers and accepted counts derive from the response, not mock objects. No customer address, access code, ID, job-rate promise or settlement amount is displayed. Invalid job links are never actionable.
- **Time correctness:** `Africa/Johannesburg` governs the current work calendar. At 22:00 UTC, the next South African day begins; regression tests cover date and year boundaries. A stale accepted booking whose scheduled start has passed is never promoted as the **next** visit, although its original schedule remains visible in Today's list.
- **Navigation and privacy:** account navigation now has a first-class Xooter Workspace entry and preserves the existing job link. Dashboard shortcuts reach Jobs, Earnings, Verification and Training. It remounts on account changes and ignores responses from obsolete requests to prevent prior-user worker details flashing across accounts.
- **Tests:** `mobile/scripts/native-xooter-dashboard.test.mts` checks owner eligibility, malformed worker projection, SAST dates, scheduled job truth, source navigation and absence of fictional payouts/private household details. Expo typecheck and full website/native CI remain release gates.

**Still open:** live signed-in worker/device acceptance, screen-by-screen native captures on iOS/Android, real Xooter bank settlement, location and timed access, full job-response transactions, app-store publication, and remaining handoff areas in this ledger. Prototype claims of "paid out every Friday", invented worker earnings and performance metrics are deliberately not copied.

## 16 October 2026 — native Xooter Growth and Badges design handoff

The original `XooterGrowthScreen` reference had a recognition hero, separate required `Xoot Standard` foundation and optional specialisms. Expo now has a dedicated `/xooter/growth` route with that source structure, native design tokens, a bounded progress bar, role-protected owner data, accessible course states, honest empty/offline handling and links from the worker dashboard and native Training.

- Source-of-truth: `training_modules` (only `id,title,description,required,duration_min,badge_label,rank_points`) and `xooter_training_progress` filtered by the signed-in user's resolved `xooters.id`. No quiz questions, answer keys, banking, addresses or private reviewer notes are queried.
- Recorded progress is derived from actual completions, not taps, mock data or prototype names/points. Duplicate module IDs or duplicate progress invalidate the summary. Orphan completions never earn points/badges. Percentages are bounded; unsafe point totals fail closed.
- A full catalogue and progress list are required to claim an exact badge/points total. Any server truncation above 100 records suppresses the summary with an explicit warning, rather than implying full completion.
- `Xoot Standard` required modules remain distinct from optional recognition. Points/badges never imply increased pay, financial transfer, verified onboarding, eligibility for assignments or automatic certification.
- Auth switching remounts the screen and discards the previous worker's catalogue/progress. Invalid reads show retry. The route does not grant progress writes or self-awarded badges.
- Negative source/data tests reside in `mobile/scripts/native-xooter-growth.test.mts` and are mandatory in `Verify approved Xoot redesign` CI.

**Still unverified:** physical iOS/Android screenshot parity with `design/handoff-2026-09-03/xoot/app/Xooter.jsx`, real logged-in training progression across staging/production, complete catalogue pagination beyond the current 100-record presentation cap, and native store distribution. This is not certification of the entire handoff.

## 17 October 2026 — native saved-place privacy and worker-ledger accuracy

The previously deployed Xooter Jobs, Earnings, job detail, Growth and training flows were already merged via PRs #62/#64/#66/#73. Obsolete development branch `design/native-xooter-jobs-earnings-20261015` must not be resurrected. Aggregation overflow/invalid sums show a recoverable integrity error instead of crashing the native screen or inventing a financial amount.
- New native regression cases exercise same-millisecond microsecond ordering, duplicated pages, swapped owner, out-of-window records, invalid cursors, sum overflow and saved-place account isolation. The approved release CI runs this suite with existing Expo/web tests.

**Not verified by static tests alone:** physical-device two-account sign-in/switch, a real paginated earnings ledger with bank-reconciled transfers, iOS/Android store distribution, accessibility screenshots, actual payout provider settlement and post-deploy financial data reconciliation.
