## What broke, and what it cost

**The live site was never the app, and the reason was not in either host.**

For three weeks `xoot.co.za` served this:

```html
<meta name="generator" content="Starfield Technologies; Go Daddy Website Builder 8.0.0000"/>
<link rel="canonical" href="https://xoot.co.za/404"/>
```

A GoDaddy Website Builder placeholder was published on the apex domain. Meanwhile **both** hosts
held correct, current production builds of `main` — Netlify `6a9808ea`, Vercel
`dpl_A5fuZXCQAPF7zCQJVKy7cAxzrPNx` — and neither received a single request.

**Three checks that were supposed to catch this, and each failed differently:**

1. `verify-live-deploy` polled for **3 minutes** under a comment claiming ~10. `attempts=12` at
   `delay=15` is eleven sleeps of fifteen seconds. Netlify's build takes longer, so it had never
   once confirmed a deploy in its entire life, and always exited **green**.
2. It printed its verdict twenty times and sent the response body — the one thing that would have
   solved this — only to the step summary, which is not readable from the API.
3. `verify-live-site.mjs`, written the day before, **had never been run by anything.**

Cost: three weeks of a live site that was not the product, and a founder repeatedly editing
credentials in a dashboard that was never in the request path.

## What I got wrong

**I closed the same gate twice on evidence that could not support it.**

First on Netlify's `currentDeploy` id changing. I caught that one myself and downgraded it.

Then on Netlify's deploy record: `ssl_url: https://xoot.co.za`, `context: production`,
`state: ready`, `commit_ref: 8cb2d0ba…`. I read that as a better proof. It is not a proof at all.

**Both mistakes have the same shape, and it is worth naming because it generalises:** a host's own
API describes *what it is configured to serve if traffic arrives.* It says nothing about where DNS
sends traffic. Vercel's `target: production, state: READY` is exactly the same class of statement.

The only thing that can answer "what does a visitor get?" is fetching the URL from outside — and
`xoot.co.za:443` is blocked by this environment's egress policy, so the question was unanswerable
from a session and had to come from a CI runner.

`domain-setup.md` had carried **"DNS is fine. Do not touch GoDaddy."** since 13 August. That
sentence is why nobody looked here for three weeks. It is corrected in place with the original text
kept, because a silently-corrected document teaches nobody.

## The decision, and the trade-off I accepted

**Merged PR #44 with a known-red check.** `verify-types` was and is failing against production,
because ~31 foreign-key constraint names never got renamed in the database and the production DB
password stored in Actions secrets turns out to be *staging's*. The drift is names only and breaks
nothing at runtime.

**Traded:** a clean board for getting the host-agnostic env fix onto `main`.
**Would reverse it if:** the drift had touched a column an application query reads. It does not —
checked across `src/` and `supabase/functions/` for embed hints and `ON CONFLICT ON CONSTRAINT`.

**Held back:** deleting production's six orphaned pre-rename Edge Functions. The dry run is done and
correct, but deletion is irreversible with no source to redeploy from, and the workflow's own
precondition — that the live site is built from this repo — is now known to be **false**.
