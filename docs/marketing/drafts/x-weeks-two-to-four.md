## Week 2 — the mechanism week

Every post this week explains **how something works**, not what happened. Testing whether mechanism
outperforms narrative at zero audience.

### X2-01 · single + artefact
> `ALTER TABLE ... RENAME COLUMN` renames the column.
>
> It does not rename the 31 constraints that reference it.
>
> A constraint name is an identifier, not a reference. Postgres has no reason to update it and does
> not.
>
> Our type check went red 952 lines. Every one of them a name.

**Visual:** the `pg_constraint` query output, cropped.
`APPROVE / EDIT / KILL`

### X2-02 · numbered list
> Four ways a check can pass while checking nothing:
>
> 1. It polls for less time than the thing takes
> 2. Its fixture was generated by the function it tests
> 3. It treats a 403 as "not ready yet" and retries until it gives up green
> 4. It has a branch that exits 0 on inconclusive and prints something reassuring
>
> We had all four. Same repo. Same quarter.

`APPROVE / EDIT / KILL`

### X2-03 · single, no artefact
> One database password. Two Supabase projects.
>
> Staging applied cleanly. Production returned `28P01` four minutes later on the same commit.
>
> The stored value was staging's, so production had never been reachable through that workflow — not
> once, since it was written.
>
> The workflow had no way to tell us. It was doing exactly what it was configured to do.

`APPROVE / EDIT / KILL`

### X2-04 · question
> Genuine question for anyone running serverless functions with a shared module:
>
> When you change the shared module, what redeploys?
>
> Ours bundles a frozen copy into each function at deploy time. So the answer was "nothing" and we
> found out with 28 of 43 functions behind.
>
> Is yours different? I would like to know I am the only one.

`APPROVE / EDIT / KILL`

### X2-05 · numbered list
> Deploy order we derived from failures, not from a blog post:
>
> 1. Migrations before functions. A function calling a column that does not exist yet fails closed
> 2. Web app before the two booking writers. The reverse ships a client that can't read what the
>    server now sends
>
> Both rules cost us an incident each. Neither is clever. Write yours down.

`APPROVE / EDIT / KILL`

### X2-06 · thread (4)
> **1/** We price every booking twice. Once in the browser so you can see the total, once on the
> server because a price the client sends is a price a client can edit.
>
> **2/** Which means the same commercial rules exist in two languages, in two files, edited months

>
> **3/** They disagreed. Three separate times. A screen showing one number and a charge taking

## Week 3 — the wrong-conclusion week

Every post is something I believed and had to reverse. Testing whether being visibly wrong
outperforms being right, at zero audience. **Prediction: it does.** MrBeast's mundane
self-deprecating post outperformed most of his spectacle.

### X3-01 · single + artefact
> I marked our site live. Twice. On two different pieces of evidence.
>
> Both wrong, both for the same reason.
>
> `ssl_url: https://xoot.co.za` from the host means *"configured to serve this domain if a request
> arrives."* It is not a statement about DNS. Nothing a host tells you is.
>
> The domain was serving a GoDaddy placeholder the whole time.

**Visual:** the `generator` meta line.
`APPROVE / EDIT / KILL`

### X3-02 · single, no artefact
> The founder told me three times that he changed the credentials in the hosting dashboard and
> nothing on the site changed.
>
> I explained it as caching.
>
> It was the actual finding, stated plainly, weeks early, by the person with the least technical
> context and the most direct evidence.
>
> Editing variables on a host nobody reaches changes nothing.

`APPROVE / EDIT / KILL`

### X3-03 · numbered list
> Three sentences in our own docs that stopped us finding a bug:
>
> 1. "DNS is fine. Do not touch GoDaddy."
> 2. "No build stamp found — this is probably fine."
> 3. A comment claiming ~10 minutes above a loop that ran for 3.
>
> All three were written by someone competent, once, and never checked again. A comment is a rumour
> with syntax highlighting.

`APPROVE / EDIT / KILL`

### X3-04 · question
> How do you find the documents in your repo that are confidently wrong?
>
> Not out of date — *wrong*, and load-bearing, so every investigation hits them and turns around.
>
> We had one carrying "DNS is fine, do not touch GoDaddy" for three weeks. I have no systematic way
> to find the next one and it bothers me.

`APPROVE / EDIT / KILL`

### X3-05 · single + artefact
> I wrote a check that fails when our live site is served by something that isn't us.
>
> Planted it against the wrong page: fired. Good.
>
> Ran it against our own page: silent. Also good — but for a reason I hadn't considered. We emit no
> `generator` at all, so it would stay silent on a 404, an empty page, or any other site that
> doesn't advertise its builder.
>
> The negative case taught me the boundary. The positive case made it look finished.

`APPROVE / EDIT / KILL`

### X3-06 · numbered list
> Rule we adopted after finding tests that asserted rules nobody had implemented:
>
> **Plant the bug. Watch it fail. Restore.**
>
> Ninety seconds. Turns a test from an assertion about the world into an observation of it.
>
> Ours had been green for weeks, adding to the count, checking nothing.

`APPROVE / EDIT / KILL`

### X3-07 · single, no artefact
> "How many tests do you have" is an input, not an outcome.
>
> The useful question is: how many have you watched fail for the reason they exist?
>
> For us that number is much smaller than the one in the summary, and I'm not going to pretend
> otherwise.

`APPROVE / EDIT / KILL`

## Week 4 — the commercial week

### X4-01 · single, no artefact
> Under South African consumer law the displayed price *is* the price. Show a total, exceed it at
> checkout, and that is a misleading representation. Intent doesn't enter into it.
>
> So every rounding default we set fails in the over-stating direction.
>
> Under-charging loses money. Over-charging is a legal problem. Those are not the same risk and
> shouldn't get the same default.

`APPROVE / EDIT / KILL`
