## 1. Set the PayFast SANDBOX secrets on the Supabase project

These are Edge Function secrets, never VITE_ variables (the merchant key does legitimately
travel to the browser in PayFast's redirect design — that is their protocol — but the passphrase
must never leave the server).

On the **staging** project first:

```bash
supabase login
supabase link --project-ref <STAGING_PROJECT_REF>

supabase secrets set \
  PAYFAST_MERCHANT_ID=10056762 \
  PAYFAST_MERCHANT_KEY=9e9440peyif5c \
  PAYFAST_MODE=sandbox \
  XOOT_APP_ENV=staging

# Optional but recommended once you have them; unset means the source-IP check logs and skips:
# supabase secrets set PAYFAST_ALLOWED_IPS=<payfast published IPs>
```

Why `XOOT_APP_ENV=staging` matters: `create-payment-session` reads capability rows per
environment and defaults to **production** when unset. Without this, staging reads production's
row (all flags false) and refuses checkout with "hosted checkout is not verified for this
provider" — the exact latent wrong-answer documented in the function.

`PAYFAST_PASSPHRASE` is intentionally NOT set for sandbox: PayFast sandbox accounts ship without
one, the signature is computed without it, and the code now allows that in sandbox mode only
(live mode still refuses to start or confirm any payment without a passphrase).

## 6. SOS — physical phone test and ops drill (the arming acceptance tests)

SOS is armed in code (`SAFETY_READINESS = "live"`, rollback instructions in
`src/lib/safety.ts`). The button now renders on the booking detail during an active visit
(en_route / in_progress) for BOTH the customer and (web) Xooter surfaces. The two acceptance
tests YOU run against a deployed build gate the public release:

**Test A — real 112 dial (physical phone):**
1. Open an active visit on the web app from a physical phone (staging first).
2. Hold the SOS button through the 5-second countdown (haptic pulse each second).
3. The phone must launch the dialler with **112** ready — before any server round trip.
4. Cancel the call. The alert has already dispatched; cancelling the ALERT now requires the
   account PIN (by design — after dispatch, the person most motivated to cancel may be the
   person the alert is about).

**Test B — operational alert drill:**
1. Dispatch a second alert (rate limit allows 10/hour).
2. Ops must receive the alert with booking + address + both identities, through the configured
   ops channel.
3. Confirm the alert row in `safety_sos_alerts` and that the cancel-PIN flow works.

**If either test fails — rollback (also documented in `src/lib/safety.ts`):**
1. `src/lib/safety.ts`: change `SAFETY_READINESS` back to `"schema_pending"`.
2. Run `npm run shared:sync` (regenerates `mobile/src/generated/safety.ts`).
3. Restore the two pinned tests (`src/lib/safety.test.ts`,
   `src/components/xoot/TrustMechanisms.test.tsx`) to expect `"schema_pending"` — they fail
   until you do, which is deliberate: nobody re-arms silently.
4. Redeploy the website. The button disappears; no data is lost, no alert is withdrawn.
   The server half (`raise-sos-alert`) is not gated by the constant and needs no rollback.

## What is intentionally NOT switched on

- **Production card payments.** The payfast production capability row is all-false. When your
  LIVE PayFast merchant credentials arrive: set them as secrets on the production project
  (with `PAYFAST_MODE=live` and a real `PAYFAST_PASSPHRASE`), pass one signed smoke test, then
  flip the production capability row — the controls are already on, so that row is the only
  remaining gate.
- **Payout execution.** `payouts.enabled` is on (as you instructed) but release still requires
  a verified payout account, no pending change request and no active hold per Xooter.
- **Recurring Care+ billing.** This loop activates a membership for 30 days; it does not yet
  charge the next cycle (no subscription/recurring agreement with PayFast is configured).
